# DM photo sharing and voice notes — design

Date: 2026-10-17 · Status: for owner review · Builds on: M3c/M3d (`files/{fileId}` + the Worker's `/files/*` endpoints)

## 1. What this is

Two new message kinds in a one-to-one chat: a photo picked from the gallery, and a voice note
recorded in the app. Both are **kinds of the file feature that already exists in code**: the metadata
document, the R2 bytes, the five Worker endpoints, the 24-hour sweep and the bucket lifecycle are
reused as they stand. Nothing here introduces a new collection, a new backend, or a new secret.

Non-goals: camera capture, saving media to the device, forwarding, reply-threads, video messaging,
end-to-end encryption, thumbnails generated by the server, group-chat attachments.

## 2. Owner decisions on record

| Question | Decision |
|---|---|
| Where does a photo come from? | Gallery only. No `CAMERA` permission, no in-app shutter. |
| How long does media live? | The same 24 hours as a text message. No "save to device". |
| Microphone | Yes — `RECORD_AUDIO` returns to the manifest, reversing an earlier removal, with a 60 s cap. |
| Re-encode | Long edge 1600 px, JPEG quality 80. |
| Image pipeline | `@capacitor/camera` v7 rather than a hand-rolled SAF + `ImageDecoder` path. |
| Recording gesture | Hold to record, release to send — with the safety rules in §8. |
| Upload rate | 30 uploads per rolling hour per user, enforced in the Worker. |

## 3. Why the pieces are where they are

**Bytes go through the Worker, not to a presigned URL.** R2 cannot bound a presigned PUT with a size
limit, a presigned URL cannot be re-authorised mid-flight, and no storage credential may reach a
device. This is already how M3d was built; media simply uses it.

**Compression is necessarily on the device.** A free-plan Worker gets 10 ms CPU per invocation and
cannot decode a JPEG, so there are no server thumbnails or transcodes. Downscaling also solves the
format problem: gallery images on modern Android are frequently HEIC/HEIF, which Chromium's WebView
cannot decode, so a picked-and-uploaded-as-is photo arrives broken. Handing `@capacitor/camera`
a resize and a JPEG quality is what keeps this from becoming our HEIC, EXIF-orientation and
picker-per-OEM bug farm to own.

**Media is fetched as a blob, not as a URL in an element.** `<img src>` and `<audio src>` cannot send
an `Authorization` header, and the download endpoint requires one. So the client does
`fetch(workerUrl, { headers: { Authorization } })` → `Blob` → `URL.createObjectURL`, revoking on
unmount and on cache eviction. A side benefit is exactly the behaviour we want: a photo that is never
opened is never downloaded.

**The message is written last, and only after `ready`.** The rules already require a referenced file
to be `state == 'ready'` and owned by the sender, so the upload completing is what unlocks the message.
A recipient therefore cannot be handed a bubble whose bytes never landed.

**Per-kind limits live in the Worker, not the rules.** A rules expression cannot branch on a MIME
prefix safely (`&&` does not reliably short-circuit, which has already cost this project two confusing
failures), and the Worker is the component that decides `ready` — so its check is the one that binds.
The rules keep validating document *shape* and the absolute 250 MiB ceiling.

## 4. Data model

`files/{fileId}` — unchanged shape plus one field, all nine keys still required:

```
senderUid, recipientUid, fileName, mimeType, declaredSize,
key, state, createdAt, durationMs
```

`durationMs` is **always present**, `0` for a photo and a generic file. It is deliberately not optional:
expressing "validate this field when it exists" in rules needs either a conditional dereference of a
missing key or a ternary, and both are the pattern that has produced spurious denials here before. One
extra integer is cheaper than that class of bug. Bounds: `is int`, `>= 0`, `<= 120_000`. It is a
client-declared UI hint, the same standing `clientAt` has — never used for a visibility or access
decision, and the player uses decoded metadata when it disagrees. The rules' 120 s is an absolute shape
guard; the Worker's 60 s is the product cap. Two different numbers on purpose, at two different layers,
and a message is capped in the UI at 60 s regardless.

`state`: `pending → uploading → ready | failed`, only ever advanced by the Worker (`allow update: if
false` for every client, already in force).

Message: `chats/{pairId}/messages/{id}` carries `fileId` as today. `chats/{pairId}.lastMessage.text`
becomes the human string `"Sent a photo"` or `"Sent a voice note"`, so the preview rules and the
existing 24-hour blanking keep working untouched.

New composite index, required by the rate cap (§6): `files` — `senderUid ASC, createdAt ASC`, declared
in `firestore.indexes.json`.

## 5. Kind resolution

The bubble's kind is derived from the MIME the **Worker accepted**, not from a client-declared field
and not from the filename:

| Stored MIME | Bubble |
|---|---|
| `image/jpeg`, `image/png` | Photo |
| `audio/mp4`, `audio/aac`, `audio/mpeg`, `audio/ogg` | Voice note |
| anything else the upload policy allowed | Generic file (open-with) |

The third row is load-bearing. A photo and a voice note are two specialised presentations of one
upload; they are **not** an exhaustive allowlist, because the generic file path M3d was built for has
to keep working for a PDF, a ZIP or a video. So the Worker's policy (§6) is a **denylist plus per-kind
caps**, and `video/mp4` legitimately lands in the generic-file row.

## 6. Worker changes

Two pure, unit-tested functions plus their call sites in `begin`:

```js
uploadPolicy(mimeType, declaredSize, durationMs) // → { ok, reason? }
rateLimitDecision(count, limit, isResume)        // → { ok, retryAfterMs? }
```

`uploadPolicy`, in order:

1. **Deny what could execute.** `text/html`, `application/xhtml+xml`, `image/svg+xml`, `text/xml`,
   `application/xml`, `text/javascript`, `application/javascript`, `application/x-msdownload`,
   `application/x-executable`, `application/x-sh` → `mime-denied`. These are the types where "the
   receiver opened a file" can turn into "script ran with the app's tokens", and none of them is a
   thing a ChatZ user means to send a friend.
2. **Images:** MIME starting `image/` (minus the denied ones) must be ≤ 8 MiB, else `image-too-large`.
3. **Audio:** MIME starting `audio/` must be ≤ 4 MiB (`audio-too-large`) and, when `durationMs > 0`,
   ≤ 60 000 (`too-long`).
4. **Everything else** is a generic file, bounded only by the rules' absolute 250 MiB ceiling.

`begin` counts that user's `files` documents created in the last hour with a `runQuery` at `limit: 31`,
so its read cost is bounded no matter how big the backlog. A request whose document already carries an
`uploadId` **that matches the document** is a resume and is not counted — otherwise a flaky mobile
connection would spend the allowance by retrying, which is the opposite of the resilience this design
promises. Refusal returns `429` with `{ ok: false, error: "rate-limited", retryAfterMs: <number> }` in
the JSON body — in the body rather than a `Retry-After` header, because every other Worker answer is
JSON and the client already has one parsing path.

`download` and `complete` do not change. Logs stay content-free: kind, uid, sizes, never a filename.

What this cap does **not** do is stop a determined actor with many accounts. It stops one friend
hammering you and one user hammering the bucket, and it is written here rather than implied.

## 7. Native layer

`RECORD_AUDIO` returns to `AndroidManifest.xml`, requested at the moment the user first presses the
mic — the same real-runtime-dialog pattern already used for notifications, with settings only as the
don't-ask-again fallback. It joins Settings → Permissions and the checklist, and a permanent denial
must surface as an honest "microphone off" state rather than a dead button (invariant 4's shape: never
fake a capability).

Three methods on the existing `VibeStats` plugin, plus a web fallback in `vibe-stats.web.ts`:

```
voiceNoteStart({ maxMs })   → { ok, reason? }        // permission + MediaRecorder begin
voiceNoteLevel()            → { level }              // 0..1, polled ~10 Hz for the meter
voiceNoteStop()             → { base64, bytes, durationMs, mime }
voiceNoteCancel()           → { ok }                 // discards the take
```

Both media paths hand JavaScript a **base64 payload and nothing else**. At 1600 px / q80 a photo is
well under a megabyte and 60 s of AAC is about 500 KB, so crossing the bridge is cheaper than the
alternative: adding `@capacitor/filesystem`, a second FileProvider authority and a native read path.
Large generic files — where base64 genuinely stops working — are M4's attachment milestone, not this
one. `MediaRecorder` writes to the app cache; the clip is never persisted beyond that cache, and an
interrupted take is discarded, not resumable.

## 8. UI surfaces

**Composer.** [app.chats.$chatId.tsx:355](file:///c:/Users/HP/Music/ChatZ/buddy-stats-chat-main/src/routes/app.chats.$chatId.tsx#L355)
is a pill input and one circular send button. A second circular button joins the row on the left, in
the same `w-9 h-9 rounded-full` family but on a muted background so it reads as secondary. It opens a
bottom sheet (`sheet.tsx`, the pattern `StatSocial` already uses) with **Photo · Voice note · File**.
In a group chat all three are absent, not greyed: groups are localStorage-only, cannot upload, and the
repo has already fixed this exact class of bug once for the Message button.

**Photo bubble.** Rounded tile at a fixed max width, intrinsic ratio once decoded, `skeleton.tsx` in
its space before then, caption below inside the same bubble when there is one. Tap opens the viewer.

**Voice bubble.** Circular play/pause, a bar series drawn from the amplitude samples actually captured
during the take, `mm:ss` from `durationMs` (corrected by decoded metadata once known), progress fill
tracking the element's clock. Starting one note pauses any other.

**Generic file bubble.** Sanitized name, size, open-with.

**Viewer.** Scrim overlay, image contain-fitted, caption, close on scrim tap or Escape. No zoom, no
save — a photo is gone in 24 hours, and a viewer offering either would be inventing capability.

**Recorder — hold to record.** Because message rules deny `update` and `delete`, a note that sends by
accident is permanent, so the gesture has to be forgiving:

- Holding inside the button records. **Release inside the button sends.**
- Drag up into the discard zone and release → thrown away, no network call.
- Release that is *ambiguous* — `pointercancel` from an edge-swipe or a shade pull, the app going
  background, an incoming call — lands in a **Send / Discard preview strip**, never sends on its own
  and never destroys the take.
- At 60 s the recorder stops into the same preview strip. It does not auto-send.
- A short tap starts the same recording in locked mode with the preview strip always — this is the
  keyboard- and switch-accessible path, and a hold-only gesture is unusable with a tremor or a
  screen reader, so it is not optional polish.
- The first press requests the microphone; the dialog consumes the gesture, so the copy is
  "Microphone access needed — hold again to record".
- The button needs `touch-action: none` and a context-menu guard, or Chromium's text-selection
  callout eats the long-press on Android.
- New controls are 44 px targets; the meter uses static bars under `prefers-reduced-motion`.

**Chats list.** No thumbnails. A preview image per thread means downloading media for every conversation
on one screen, and it would put someone's photo on a shared device's notification-free list view.

**Structure.** `app.chats.$chatId.tsx` is already 717 lines; three bubbles, a recorder and a viewer
would take it past 1100. New `src/components/dm/`: `MediaSheet`, `PhotoBubble`, `VoiceBubble`,
`FileBubble`, `VoiceRecorder`, `PhotoViewer`, `MediaPreviewStrip`. New `src/lib/media-repo.ts`:
`uploadMedia()`, `loadMediaBlob()` (LRU of 8, revokes object URLs on eviction and unmount),
`mediaKind()`. `Bubble` becomes a thin dispatcher. `src/lib/dm-repo.ts` gains `sendMedia()` and the
`Message` type gains `fileId`.

## 9. Failure states

Each is a named client state with its own copy. There is no single "failed to load".

| Point of failure | Behaviour |
|---|---|
| Picker or sheet dismissed | No-op. No toast, no document. |
| Source unreadable / won't compress | "That photo couldn't be read" / "won't compress small enough". |
| Declare fails (offline, rules refusal) | Nothing appears in the thread. Correct, and no orphan. |
| MIME or size refused by the Worker | The reason comes back as a code and is shown as itself. |
| Rate limited | "You've sent a lot recently — try again in N minutes." |
| Upload interrupted mid-part | `begin` returns the same `uploadId` and part plan; the client resumes. |
| Size drift at `complete` | Document → `failed`, object deleted, **no message written**. |
| Upload OK, message write fails | A pending-media tray entry with **Retry that re-attempts only the write**. If abandoned, the unpointed document expires at 24 h and the lifecycle takes the bytes. |
| `401` on download | Refresh the ID token once, then ask to sign in again. |
| `403` | "This message is no longer available" — the friendship ended after the message arrived. |
| `410` | "Expired." |
| `404` | "Removed by the sender." |
| `502` / `503` | "Couldn't load — tap to retry." |
| Offline | "Needs a connection." |
| Mic denied | Button stays, explains itself, links to Settings → Permissions. |
| Recorder interrupted | Preview strip. |
| Web build | Mic row absent; `vibe-stats.web.ts` reports unavailable. |

No media is cached on device, because a cache would outlive the 24 hours that justifies deleting the
file. `isExpiredDoc()` already ages a bubble out before a fetch is attempted.

## 10. Privacy and security

Photos and voice notes are user content: never logged by the Worker (kind, uid and byte counts only),
never in a notification body beyond "sent you a photo", and lock-screen text stays the sanitized
`publicVersion`. Downloads keep `Content-Disposition: attachment` and `X-Content-Type-Options:
nosniff` with both RFC 6264 filename forms, because the content type is uploader-supplied and nothing
verifies it — an SVG or an HTML file posing as a PDF must not execute in the app's WebView. Unfriending
or blocking revokes access through the same `areFriends()` check that already guards chats, re-verified
by the Worker at download time rather than trusted from the document. `FLAG_SECURE` already covers the
whole window, so an opened photo cannot be screenshotted; the Google account picker, system settings
and the installer are separate windows and remain outside it, and an external camera was never in
scope. The key is always rebuilt from the document, so no request can address another user's prefix.

## 11. Cost, checked against the free tiers

Expiry converts storage into a **constant** rather than a accumulation: at 24 hours, stored bytes are
roughly one day of traffic. 2,000 media items a day at ~450 KB is ~0.9 GB — against R2's free 10
GB-month. Class A ops are ~3 per upload, Class B ~1 per download; free is 1M and 10M per month.
Workers free is 100k requests/day, and one media send is `begin` + one `part` + `complete` = 3, with
one download on the far side, so requests are not the ceiling either.

**The binding constraint is Firebase Spark writes.** Each photo costs roughly 8 Firestore writes across
the two devices (sender: document create, the Worker's `uploading` and `ready` patches, message create,
chats merge; recipient: the read marker; then retention's two deletes). At ~20k writes/day that is on
the order of 2,000–2,500 media messages per day for the whole user base, shared with every other write
in the app. This is stated because it is the number to watch, not R2 — and the 30/hour cap exists
partly to keep one user from spending everyone's budget.

## 12. Testing

1. **Rules, emulator suite.** `durationMs` accepted as an in-range integer; refused when negative,
   fractional, over 120 000, or a string; documents missing it refused. One test that deliberately
   **passes** a `video/mp4` declaration, pinning the boundary we chose: rules validate shape, the
   Worker owns media policy. Plus the guard-proofing this repo already does — each new clause
   removed once, its test shown to fail.
2. **Worker, pure policy tests.** The whole `uploadPolicy` table: every denied MIME (the safety
   refusals that matter are `text/html`, `image/svg+xml`, `application/javascript`,
   `application/x-msdownload`), every cap boundary at exactly-in and +1, `durationMs` at 60 000 and
   60 001, an empty and an oversized MIME string, and — the one that keeps §5 honest — `video/mp4`
   **accepted** as a generic file. Plus `rateLimitDecision` at 29 / 30 / 31 / resume-at-31. No stubbed
   bucket: a stub only proves the code agrees with itself.
3. **Live bucket smoke checklist** (after M3e, with a real device token): single-part photo — which
   also settles whether R2 accepts a one-part `complete()` — 8-part file, deliberately wrong
   `declaredSize` ending `failed` with no message, an upload killed mid-part and resumed, recipient
   download, unfriend-then-download → 403, expired → 410.
4. **Device, Infinix.** HEIC → JPEG verified by reading magic bytes of the returned file, not by
   trusting the plugin; EXIF orientation on a portrait shot; 60 s cap reaching the preview strip;
   denied-mic state; long-press not raising the selection callout; `pointercancel` mid-hold via a shade
   pull showing Send / Discard; airplane mode between upload and write, then Retry performing only the
   write; `dumpsys meminfo` across 50 photo bubbles with the LRU actually revoking URLs; token expiry
   during a download; TalkBack reading a photo and an expired note as different things.
5. **Gates, run as CI runs them.** `npm run test:rules`, `npx tsc --noEmit`, scoped `eslint`,
   `npm run build` with the bundle-size delta reported, and `node scripts/retention-dry-run.mjs` before
   any delete is ever enabled.

## 13. Sequencing

Dependencies first, both already pending the owner's approval: **M3e** (create `chatz-files`, bind it,
set the 1-day lifecycle, deploy the Worker) and **V2** (publish `firestore.rules`). Neither can be
skipped: nothing in this spec is device-testable without a live bucket, and the message-`fileId` rule
is part of the same un-published rules file.

Then, one milestone with reviewable commits: **M4a** rules + Worker policy + index and their tests;
**M4b** photo path end to end; **M4c** voice notes; **M4d** generic-file bubble and open-with, the
first place base64 stops being enough. Design and accessibility review lands with each of M4b and M4c.

## 14. Not verified, and flagged as such

- **`@capacitor/camera` option names.** Two doc fetches in this session returned answers from an
  unrelated proxy URL and are not trustworthy (`quality`/`width`/`height`/`resultType` are plausible,
  not confirmed). The implementation must read the installed package's own `definitions.d.ts` before
  writing a call, and the resize/quality behaviour must be confirmed on the device by magic-byte and
  dimension checks.
- **R2 accepting a one-part `complete()`.** Presumed from S3 semantics; only the M3e smoke test proves
  it. If it is refused, the fix is a `count === 1` branch that uses `put()`.
- **Whether `@capacitor/camera` re-encodes on the web build** to the same 1600 px / q80. The web path
  is a development convenience, and if it does not re-encode, the web build refuses the send rather
  than uploading an original.
- **EXIF orientation and picker behaviour on XOS/ColorOS specifically** — device-test items, not
  knowledge.
- **A real measurement of per-photo Firestore write cost** (the ~8 in §11 is arithmetic on the code
  paths, to be confirmed by `scripts/retention-dry-run.mjs`-style counting during M4b).

## 15. Known gaps accepted for now

No per-photo delete or unsend (message rules deny both, by design). No forwarding. No reply to a
specific photo. No virus or malware scanning of uploaded bytes — the bucket is private and the only
exit is an authenticated `attachment`, so the exposure is a user downloading their friend's file, not
a public host. No account-level abuse ceiling beyond the 30/hour per-user one. No image in the
notification shade.
